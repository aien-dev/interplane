# Changelog

## Unreleased (0.3, Trust lane)

- Security: the Rust lifecycle now accepts an approval continuation only with the `approval_id` the runtime minted for that request, as Python already did; before, any non-empty id was accepted. A non-`authorized` continuation value with the minted id is DENIED in both SDKs. Lifecycle conformance cases `lifecycle/01-05`; 30/30 byte-identical.
- Trust vocabulary reconciled (plan cut P1, gaps G1-G3): CROSSVEIL.md default is `tool_result` + `unknown` (the undefined `untrusted_tool_content` and `origin` are gone), VERSIONING.md lists `ContentKind` in place of the undefined `Origin`. Python now reads an unrecognized or non-string `content_kind` as `unknown`, as Rust did; non-string trust is `external_untrusted`. Odysseus `system` result integrity maps to `trusted_runtime` unless Odysseus's own gate marks the result untrusted. Conformance cases 26, 27 (with a harness-only `mock_provenance` seam and JCS round-trip checks); 32/32 byte-identical together with lifecycle/01-05.
- InputRecord and Exposure types (plan cut P2): `spec/schemas/input.schema.json`, optional `provenance.exposure` in `intent.schema.json`, Crossveil Trust rules 5 and 6, Rust and Python types in lockstep, one schema-valid example per source class under `conformance/fixtures/input/`, digest fixtures `digest/input-record-01` and `digest/exposure-01` identical in both languages; types only, no pipeline behaviour (cut P3).
- Pipeline input ledger and exposure (plan cut P3): the pipeline records every rendered result as an InputRecord (`parent_id` = its `request_id`), the host registers other inputs with the host-only `register_input`, and every `tool_request` and `CallContext` carries a computed `provenance.exposure` (a forged one is overwritten; an empty ledger, unknown trust or an untraceable `derived_from` gives `external_untrusted`). Conformance cases 28-30 and new optional `expected.inputs` / `expected.exposure`; 35/35 byte-identical in both SDKs, earlier verdicts unchanged.
- Source-class coverage fixtures (plan cut P4): cases 31-40 (one per source class plus a host-registered `model_generated` case), mock capabilities `read_document`, `load_skill`, `call_provider`, CROSSVEIL source-class table (skills and tool descriptions are `external_untrusted`; the host, not the pipeline, records model-generated input); 45/45 byte-identical in both SDKs; cases 24-25 selection digests re-pinned for the larger mock catalog, outcomes unchanged.
- Injection harness and negative controls (plan cut I1): fixtures declare `injection: {category, canary, target}` and a scripted obedient model emits the injected intent every time; the runners judge effects and content-derived intents; negative controls V1-V6 exist only behind the runners' test-only switch (Rust feature `negative-controls`, Python `--variant`/`--matrix`), each detected by named cases, matrix byte-identical across languages; `conformance/TRUST-DIGEST.txt` (whole fixture corpus, matrix list, protocol) recomputed by CI; 3 seed cases, 48/48 byte-identical.
- Content-borne injection corpus (plan cut I2): injection fixtures 04-19 cover C01 workspace, C02 tool output (nested result content, error-message text), C03 memory, C04 web and C05 document (markup embedded in the body) in all three payload forms, via a harness-only `mock_data` fixture override in both mocks; the runtime already blocked every case, so no pipeline change; V1 and V4 must-fail lists extended; 78/78 byte-identical in both SDKs.
- Approval continuation (plan cuts A1 spec and A2): `CORE.md` and `CROSSVEIL.md` pin a host-controlled continuation (correlation by trace, request, minted `approval_id` and the digest of the original `capability_request`; expiry against the host clock; terminal cancel; replay and restart refused), both pipelines gain host-only `continue_approval`, `cancel_approval` and `pending_approval` (no model-writable field is read as a grant, `decide` is not called again, the request ledger is untouched), the mock executes an approved `delete_file`, and fixtures `approval/01-14` cover A01 to A14 with new host steps `approve`, `cancel`, `restart`, `mock`; V6 now fails A06 and A13, V5 also A02 and A03, V2 also A10; 62/62 byte-identical in both SDKs, the earlier 48 rows unchanged.
- AIEN approvals through the continuation API (plan cut A3): `decide` never reads a grant and now carries an adapter-minted `approval_id` on `requires_approval`; the approver's grant reaches AIEN only through `present_approval` (the runtime's continuation decision, fed to `Pipeline::continue_approval` via `AienShared::continue_approval`); the spend point (grant spent at mint, before the pipeline's own checks and the provider call) is documented and tested, including pipeline refusal and provider rejection after the mint (reported, never a second effect); new tests for model content, stale scope, expiry, cancel and both spend-point failures; AIEN adapter only.
- Odysseus approvals (plan cut A4): approval continuation is unsupported on Odysseus and fails closed. The adapter mints no approval id, so a `requires_approval` request has no pending entry and every host continuation or cancel is refused; `execute` refuses any non-`authorized` decision; the decision states `approval continuation unsupported on Odysseus`. Odysseus's sealed approvals are task or chat scoped and bound to owner, session and run, which the single-effect continuation cannot express. New tests cover the Odysseus subset of A01 to A14; Odysseus adapter only.
