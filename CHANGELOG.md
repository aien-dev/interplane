# Changelog

## Unreleased (0.3, Trust lane)

- Security: the Rust lifecycle now accepts an approval continuation only with the `approval_id` the runtime minted for that request, as Python already did; before, any non-empty id was accepted. A non-`authorized` continuation value with the minted id is DENIED in both SDKs. Lifecycle conformance cases `lifecycle/01-05`; 30/30 byte-identical.
- Trust vocabulary reconciled (plan cut P1, gaps G1-G3): CROSSVEIL.md default is `tool_result` + `unknown` (the undefined `untrusted_tool_content` and `origin` are gone), VERSIONING.md lists `ContentKind` in place of the undefined `Origin`. Python now reads an unrecognized or non-string `content_kind` as `unknown`, as Rust did; non-string trust is `external_untrusted`. Odysseus `system` result integrity maps to `trusted_runtime` unless Odysseus's own gate marks the result untrusted. Conformance cases 26, 27 (with a harness-only `mock_provenance` seam and JCS round-trip checks); 32/32 byte-identical together with lifecycle/01-05.
- InputRecord and Exposure types (plan cut P2): `spec/schemas/input.schema.json`, optional `provenance.exposure` in `intent.schema.json`, Crossveil Trust rules 5 and 6, Rust and Python types in lockstep, one schema-valid example per source class under `conformance/fixtures/input/`, digest fixtures `digest/input-record-01` and `digest/exposure-01` identical in both languages; types only, no pipeline behaviour (cut P3).
- Pipeline input ledger and exposure (plan cut P3): the pipeline records every rendered result as an InputRecord (`parent_id` = its `request_id`), the host registers other inputs with the host-only `register_input`, and every `tool_request` and `CallContext` carries a computed `provenance.exposure` (a forged one is overwritten; an empty ledger, unknown trust or an untraceable `derived_from` gives `external_untrusted`). Conformance cases 28-30 and new optional `expected.inputs` / `expected.exposure`; 35/35 byte-identical in both SDKs, earlier verdicts unchanged.
- Source-class coverage fixtures (plan cut P4): cases 31-40 (one per source class plus a host-registered `model_generated` case), mock capabilities `read_document`, `load_skill`, `call_provider`, CROSSVEIL source-class table (skills and tool descriptions are `external_untrusted`; the host, not the pipeline, records model-generated input); 45/45 byte-identical in both SDKs; cases 24-25 selection digests re-pinned for the larger mock catalog, outcomes unchanged.
- Injection harness and negative controls (plan cut I1): fixtures declare `injection: {category, canary, target}` and a scripted obedient model emits the injected intent every time; the runners judge effects and content-derived intents; negative controls V1-V6 exist only behind the runners' test-only switch (Rust feature `negative-controls`, Python `--variant`/`--matrix`), each detected by named cases, matrix byte-identical across languages; `conformance/TRUST-DIGEST.txt` (whole fixture corpus, matrix list, protocol) recomputed by CI; 3 seed cases, 48/48 byte-identical.
- Content-borne injection corpus (plan cut I2): injection fixtures 04-19 cover C01 workspace, C02 tool output (nested result content, error-message text), C03 memory, C04 web and C05 document (markup embedded in the body) in all three payload forms, via a harness-only `mock_data` fixture override in both mocks; the runtime already blocked every case, so no pipeline change; V1 and V4 must-fail lists extended; 78/78 byte-identical in both SDKs.
- Mock effect policy (plan cut E1): the CORE.md mock table gains a Class column (`read` or `effect`); an `effect` the table would authorize is `requires_approval` when `CallContext.exposure.floor` is below `user_supplied` or absent. Cases 19 and 27 register the user request first; case 40 now expects its second `append_note` held; injection 43 (web) and 44 (memory) target `append_note`. 105 verdict rows, identical in both SDKs.
- Odysseus adapter consumes exposure (plan cut E2): the untrusted-context gate is armed from `CallContext.exposure` (floor below `user_supplied`, or missing: fail closed) as well as Odysseus's own `observe_tool_result`; the caller-supplied `trust` / `prior_trust` path is removed. `demo.register_user_turn` records the user's request; the demo, the adapter tests and `bench/tools/run_bench.py` use it, so future bench runs start each trace at `user_supplied` (the 0.2x campaign runs pinned code and is unaffected). New `tests/test_injection_exposure.py`: 91 adapter tests pass.
- AIEN adapter exposure and labels (plan cut E4): re-pinned to aien-sovereign-core 0c1d249 (#207, exposure-aware authority; PROTOCOL-0.3 T4 pin recorded here). `decide` hands `CallContext.exposure` to `EffectLane::with_exposure` and keeps it per request for the grant path; effects under a floor below `user_supplied` (or absent) are held with a reason naming exposure. Results are labelled by capability instead of always `workspace_content`. New `tests/exposure.rs`; 33 adapter tests pass.
- Approval continuation (plan cuts A1 spec and A2): `CORE.md` and `CROSSVEIL.md` pin a host-controlled continuation (correlation by trace, request, minted `approval_id` and the digest of the original `capability_request`; expiry against the host clock; terminal cancel; replay and restart refused), both pipelines gain host-only `continue_approval`, `cancel_approval` and `pending_approval` (no model-writable field is read as a grant, `decide` is not called again, the request ledger is untouched), the mock executes an approved `delete_file`, and fixtures `approval/01-14` cover A01 to A14 with new host steps `approve`, `cancel`, `restart`, `mock`; V6 now fails A06 and A13, V5 also A02 and A03, V2 also A10; 62/62 byte-identical in both SDKs, the earlier 48 rows unchanged.
- AIEN approvals through the continuation API (plan cut A3): `decide` never reads a grant and now carries an adapter-minted `approval_id` on `requires_approval`; the approver's grant reaches AIEN only through `present_approval` (the runtime's continuation decision, fed to `Pipeline::continue_approval` via `AienShared::continue_approval`); the spend point (grant spent at mint, before the pipeline's own checks and the provider call) is documented and tested, including pipeline refusal and provider rejection after the mint (reported, never a second effect); new tests for model content, stale scope, expiry, cancel and both spend-point failures; AIEN adapter only.
- Odysseus approvals (plan cut A4): approval continuation is unsupported on Odysseus and fails closed. The adapter mints no approval id, so a `requires_approval` request has no pending entry and every host continuation or cancel is refused; `execute` refuses any non-`authorized` decision; the decision states `approval continuation unsupported on Odysseus`. Odysseus's sealed approvals are task or chat scoped and bound to owner, session and run, which the single-effect continuation cannot express. New tests cover the Odysseus subset of A01 to A14; Odysseus adapter only.
- Authority-claim, identity, catalog and fault corpus (plan cuts I3 and I4): injection fixtures 20-42 cover C06 to C09, C11, C12 and C13, plus approval fixtures 15 and 16 (explicit `denied`, decision citing another request); pipeline fixes in both SDKs: a result citing another `request_id` now fails the request, a duplicate advertised capability name with differing definitions is rejected as `stale_capability`, and Python's decide-fault, mismatched-decision and execute-fault outputs now match Rust; V7 and V8 added; 103/103 byte-identical.
- Adapter subset runners (plan cut R0, prerequisite for REPORT-0.3): the normative T3/T4 subset rule and fixture translation (`spec/CORE.md`, Adapter subsets; `conformance/adapter-translation.json`), `t3_subset` (43) and `t4_subset` (31) frozen in `TRUST-DIGEST.txt`, T3 runner `python -m interplane_adapter_odysseus.t3` and T4 runner `adapters/aien/tests/t4_corpus.rs` run through the real Pipeline and adapter and wired into CI; violations 0 and content-derived 0 over both subsets.
- Protocol case A15 as a corpus fixture (plan cut R0b): `approval/17-provider-fails-after-approval` (approved effect fails at the provider after the approval was spent; reported, request terminal, second continuation refused). Mock `execute_raises` on T1/T2; on T4 a real write into a missing directory, rejected by the AIEN write provider. Corpus 106 rows, gate I 60 cases, T4 subset 32; T3 unchanged at 43.
- Trust run tooling (plan cut R1a): both conformance runners write `<case>.inputs.json` (full input ledger) next to `<case>.results.json` under `--dump`, byte-identical across Rust and Python (the Rust results dump now nulls `duration_ms` like Python). `bench/tools/trust_run.py` runs every offline leg of PROTOCOL-0.3 (T1, T2, both negative-control matrices, validator, TRUST-DIGEST, T3, T4) and computes gates P, X, I, E, A, N from the raw files. The dev run found a spec-versus-protocol conflict: results the pipeline synthesizes after a raising or foreign-result `execute` carried null `content_kind` and `trust` (CORE.md said so), which gate P2 counts as missing. Both pipelines now label them `tool_result` + `unknown`, the schema reading of a null label, so behaviour is unchanged.
- Streamed responses (plan 19.7 item 6, streaming half): Lenshift dialect `openai_stream` in Rust and Python takes a streamed `/v1/chat/completions` body (Server-Sent Events) exactly as sent, assembles the fragments into one assistant message and parses it with the `openai` rules (`spec/LENSHIFT.md`). A stream without `finish_reason` `stop`, `tool_calls` or `function_call` rejects every call as "truncated tool call"; malformed streams (conflicting id or name, second choice, fragment without index, data after `[DONE]`, non-JSON chunk) are rejected whole. 23 dialect fixtures, six of them the real Ollama, llama.cpp and SGLang stream captures byte for byte. Both dialect fixture runners now also compare every digest a fixture records.
- Lenshift `openai` cross-language fix: Rust accepted an already-decoded `arguments` object and reported a non-string value as "arguments is not an object"; it now rejects every non-string `arguments` as "arguments is not valid JSON", as Python and `spec/LENSHIFT.md` do. Only Ollama's own `/api/chat` sends decoded objects (capture `05e`); all 29 OpenAI-compatible captured calls send strings. Fixtures `openai/arguments_decoded_object` and `openai/arguments_not_string` fail on the old Rust code.
- Session state limits (plan 19.7 item 6b): host-set `max_traces` (1024), `max_messages_per_trace`, `max_requests_per_trace` and `max_inputs_per_trace` (4096 each) bound the pipeline's per-trace state in Rust and Python. A message or request over a limit is refused at the replay and duplicate stage with the new `ErrorCode` `session_limit_exceeded` (`session limit exceeded: <limit name>`), after the replay and duplicate checks and before any runtime contact; `register_input` over its limit fails like a duplicate `input_id`. New host-only `Pipeline.close_trace` drops a trace's ledger ids, inputs, approval entries, event sequence and events and refuses later messages, requests, inputs and approval continuations with the new `session_closed` (`session closed: <trace_id>`). Unit tests with the same scenarios in both SDKs (the 0.3 corpus stays frozen). Python: the trace flag `_pending` is renamed `_awaiting`.
- Refused calls use their request id (cross-language fix): Python `run_turn` did not record the `request_id` of a malformed or over-the-turn-limit call, Rust did, so a later call reusing that id was a duplicate in Rust and accepted in Python. Python now records it like Rust (within the session state limits); `spec/CORE.md` states the rule. Same test in both SDKs; it fails on the old Python.
- Gate M and trust-run verdicts no longer pass vacuously. `bench/tools/live_injection.py`: `summarize([])` returned `gate_violations_zero: true` with zero cases, and a `--only` subset run printed "Gate: PASS" and exited 0. The summary now carries `verdict` (PASS, FAIL, EXPLORATORY, INCOMPLETE), `qualifying`, `completeness` (missing, duplicated, unexpected, errored cases) and `preregistered` (case count, `case_set_digest`, freeze match against `conformance/TRUST-DIGEST.txt`); PASS needs the whole preregistered C01-C08 + C11 set, run exactly once, no error, frozen corpus, 0 violations, and `gate_violations_zero` is true only then. Existing summary fields keep their names. Exit code 3 for EXPLORATORY or INCOMPLETE. `bench/tools/trust_run.py`: gate X passed on zero verdict rows and gate E on zero injection cases; X now needs exactly the corpus rows and E needs every system to cover its whole injection set (T1, T2: all injection fixtures; T3, T4: the frozen subsets). `analyze.py` already reports INCOMPLETE on a partial or vacuous run (checked, unchanged). Tests in `test_live_injection.py` and `test_analyze.py`.
