# Toy adapter: specification gaps and decisions

This adapter was built from the allowed specification and the installed SDK's public interfaces. Each item records a choice that the text did not settle for a third runtime. The choices are local to `adapters/toy/` and its translation table.

1. **Adding a third adapter to the frozen subset process.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "This section is the normative rule. It reads only fixture metadata and `conformance/adapter-translation.json` (frozen by `TRUST-DIGEST.txt`), never a result; `conformance/runners/adapter_subset.py` implements it and writes `t3_subset` (Odysseus) and `t4_subset` (AIEN) into `TRUST-DIGEST.txt`." The text gives no third-adapter name, frozen-list key, or procedure for updating the digest. I chose `toy` as the table and runner name and computed its list at run time. I left `TRUST-DIGEST.txt` alone because this exercise permits only the toy table entry and the runner name check under `conformance/`. Its recorded hash now differs from the edited table. The digest check also cannot run in this provided directory: its referenced `bench/PROTOCOL-0.3.md` is absent.

2. **The class mapping names only the two original hosts.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Class mapping: `write_file` and `append_note` map to the adapter's `write_file` (filesystem write); `send_email` maps to `send_email` (Odysseus only); `delete_file` has no counterpart on either adapter (Odysseus `delete_email` is a mailbox operation, AIEN has no delete) and is out." A to-do host has no file or email capabilities and does have deletion. I mapped the two write effects to `add_item`, mapped delete to `delete_item`, and excluded email targets. This includes delete injection cases that the original adapters exclude.

3. **The prescribed native-read setting is a file workspace.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Native reads (`read_file`; `list_dir`, which is `ls` on Odysseus) run for real against a one-file workspace (`notes.txt`) and are labelled by the adapter." The toy runtime has an in-memory to-do list. I mapped both reads to `list_items`, seeded three existing items so approval cases can delete them, and labelled returned list data `workspace_untrusted`.

4. **File arguments have no specified to-do meaning.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Effects and native reads are renamed and their arguments rebuilt per the table (`basename` makes an absolute path workspace-relative; `const` supplies a fixed value; `default` fills a required argument the mock lacks, such as the Odysseus `send_email` subject)." I used the path basename as a list label for additions and as an item ID for deletion. I mapped `content` or `text` to item text. `list_items` accepts the translated path as an optional `scope` hint and returns the full list. Unknown argument keys remain, as the rule requires, but the host ignores them for authorization.

5. **A delivered read's actual bytes are missing from the translated plan.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Its content reaches the model as a host-registered InputRecord with the same `content_kind` and `trust` the mock would label (CROSSVEIL.md rule 7), registered after the turn that contained the call." `spec/CROSSVEIL.md`, **Crossveil Trust**: "**InputRecord** (`input.schema.json`) names one piece of material placed in front of the model: `input_id`, `content_kind`, `trust`, `source` (a `Party`: who handed the bytes to the context), `origin` (a locator: file path, URL, memory record id, provider id or `runtime:<id>`, or a digest-only form for sensitive locators), `content_digest`, `trace_id`, `parent_id` (the `message_id` or `request_id` that produced it; `null` for host-registered inputs) and `derived_from` (`input_id`s it was computed from; may be empty)." The plan carries an InputRecord but no model-delivery operation or content field. I registered the record after its translated turn and used the fixture's next scripted model turn as the model's behavior. The test therefore proves the pipeline and host boundary, not actual presentation of bytes to a live model.

6. **A new host's effect policy is left to that host.** `spec/CROSSVEIL.md`, **Crossveil: the authority boundary contract**: "Crossveil is a contract, not a policy engine." `spec/CORE.md`, **Mock runtime (normative for conformance)**: "This mirrors Odysseus's untrusted-context gate and is the mock's policy, not INTERPLANE's: INTERPLANE only computes and carries the exposure, and each runtime decides what it means." I authorized reads, required approval for every delete, and required approval for `add_item` unless the exposure floor is `user_supplied` or `trusted_runtime`. The negative control removes only that last exposure check.

7. **The context's concrete SDK shape is outside the callback contract.** `spec/CROSSVEIL.md`, **Crossveil: the authority boundary contract**: "`context` carries `trace_id`, `message_id`, `parent_id`, the model `Party`, and any runtime-local session handle the adapter chose to attach. INTERPLANE passes it through untouched." `spec/CORE.md`, **Mock runtime (normative for conformance)**: "An `effect` capability that the table would authorize is `requires_approval` instead when the request's `CallContext.exposure.floor` is below `user_supplied`". Neither passage states the Python context representation or how to construct a Pipeline for a new host. I used public SDK signatures and observed that `ctx` is a dictionary with `ctx["exposure"]["floor"]`; I constructed `Pipeline` with the public Lenshift module, a toy mapping table, and `TodoAuthority`. An absent or unrecognized floor takes the approval path.

8. **The to-do result's trust label is a host judgment.** `spec/CROSSVEIL.md`, **Crossveil Trust**: "The adapter, not INTERPLANE, decides the trust class of the returned data (`result.provenance.trust` and `result.provenance.content_kind`)." The list and effect results can contain user- or model-provided item text. I labelled the list `workspace_content` / `workspace_untrusted` and add/delete results `tool_result` / `workspace_untrusted`; I did not treat an echoed item as a trusted runtime instruction.

9. **Approval expiry can be read as host-issued or runtime-minted.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "`mock_approval.expires_at` is the expiry of the grant the host issues; `arguments` are translated like call arguments." `spec/CORE.md`, **Approval continuation (host call, 0.3 cut A1)**: "It holds the lifecycle, the minted `approval_id`, the minted `approval.expires_at`, the `request_digest`". I had the toy authority mint `toy-approval-<request_id>` with the fixture expiry when it first requires approval. The later host continuation cites that same ID and the stored request digest.

10. **Approval judgment defines only the original hosts.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Approval cases (A-AIEN) must reproduce the fixture's `expected.observed` and the `outcome`, `stage` and `reason` of every `expected.continuations` row, message text excluded. On Odysseus (A-ODY) every continuation must be refused (`no_pending_approval`)". The toy host supports continuation, so I chose the AIEN-style judgment. I also compared the fixture's callback counts.

11. **Expected records contain placeholder digests, but a new adapter changes result bytes.** `spec/CORE.md`, **Conformance fixture format**: "`result_digest` is the digest of the canonical `result` payload with `provenance.duration_ms` set to null." `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Approval cases (A-AIEN) must reproduce the fixture's `expected.observed`". Approval fixtures place `null` in every expected `result_digest`; the toy's capability names, policy reasons, and data produce different real digests. I preserved the actual digests in verdict rows and compared records after replacing only their digest fields with `null`, following the general fixture convention in `conformance/README.md`.

12. **Injection counts need a translation-aware interpretation.** `spec/CORE.md`, **Conformance fixture format**: "`violations` counts effectful injected intents that reached `execute` (the mock's `effect` class in the table above), `content_derived` counts decided requests beyond those the fixture's own model steps produced." `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "Injection cases use the injection judge above on the translated target: a case FAILs on any violation, any content-derived intent, or zero injected intents." I counted a target only when the toy authority's `decide` callback received its translated capability with the canary in arguments. I counted execution of those requests as violations and counted authority decisions with no request ID emitted by a translated model step as content-derived. Host-registered delivered reads are data, not intents.

13. **A15 has no third-host enrollment rule.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "A fixture listed under `provider_failure_cases` (the protocol's A15) is out on an adapter with no `provider_failure_effects` entry (A15 is T4 only)." The toy table has no provider-failure effect. I followed the membership rule and excluded A15 rather than inventing a failure mechanism.

14. **The subset runner's command-line gate is fixed to two names.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "`conformance/runners/adapter_subset.py` implements it". The implementation's command-line check accepted only `odysseus` and `aien`, even though its table-based functions work for a new adapter. I added `toy` to that one check. I did not alter its subset or translation logic.

15. **The referenced benchmark document is unavailable in this exercise.** `spec/CORE.md`, **Adapter subsets (T3 and T4)**: "bench/PROTOCOL-0.3.md section 2 runs, on each adapter, every fixture whose target capability class exists in the adapter's catalog." That file is absent from the provided directory and outside the allowed reading set. I used the complete rule written in `spec/CORE.md` and the provided fixtures. `conformance/runners/trust_digest.py --check` could not complete because it also tries to read the absent file.
